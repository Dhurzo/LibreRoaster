# Milestone v4.0: Async Sensor Race Condition Fix

**Status:** ✅ SHIPPED 2026-02-20
**Phases:** 58-61
**Total Plans:** 7

## Overview

Replaced the unsafe take/replace pattern in `roaster_async_sensor_read()` with an `embassy_sync::Mutex`-backed API, closed ASYNC-06 with a host concurrency harness plus lock-depth telemetry, and wired the USB instrumentation hook so every exported helper is exercised and documented.

## Phases

### Phase 58: Async Mutex Migration

**Goal**: Migrate `ServiceContainer` to `embassy_sync::Mutex`, preserve ISR compatibility with a deprecated sync path, and eliminate the take/replace race window by switching async callers to `lock().await`.
**Depends on**: Phase 57 (security rollup & protocol references)
**Plans**: 5 plans

Plans:

- [x] 58-01: Async mutex migration — dual EmbassyMutex/critical_section fields, async helpers, and sync deprecation
- [x] 58-02: Async lock pattern migration — all async callers now await `with_roaster_async()` instead of the old API
- [x] 58-03: Test integration summary — sync helpers preserved, USB tasks and mock UART tests updated to the new wrapper
- [x] 58-04: ISR sync access verification & race confirmation — deprecated methods remain for ISR contexts while `lock().await` blocks race conditions
- [x] 58-05: ASYNC-06 closure — host concurrency test proves the mutex tolerates parallel sensor reads

**Details**:

The migration rewired `ServiceContainer` to hold both `roaster: EmbassyMutex` and `roaster_sync: critical_section::Mutex`, added `with_roaster_async()`, deprecated the sync helpers, and ensured every async `roaster_async_sensor_read()` caller awaits the mutex guard. The new lock semantics guarantee only one async task can hold the mutex at a time, releasing the guard automatically and removing the take/replace window.

### Phase 60: Concurrent Sensor Read Integration Test

**Goal**: Add a host-side harness that runs multiple `roaster_async_sensor_read()` futures in parallel, captures `max_async_lock_depth`, and documents how to replay the proof for ASYNC-06.
**Depends on**: Phase 59 (queue instrumentation from command transport resilience)
**Plans**: 1 plan

Plans:

- [x] 60-01: Concurrent sensor read instrumentation harness with guard metrics and README instructions

**Details**:

The host test spawns ten concurrent sensor reads with `ThreadPool::spawn_with_handle`, asserts every result is `Ok`, and records instrumentation via the `async-lock-depth-metrics` feature. Helpers reset the metrics before/after each batch to keep telemetry reproducible, and the README now details how to run the harness and cite ASYNC-06 coverage for audits.

### Phase 61: USB Instrumentation Wiring

**Goal**: Wire `process_usb_command_data_test` into a riscv32-only harness, reset the USB queue before/after the hook, and surface the instrumentation to auditors.
**Depends on**: Phase 59 (USB queue helpers from command transport resilience)
**Plans**: 1 plan

Plans:

- [x] 61-01: USB instrumentation runner + documentation that proves the helper is consumed

**Details**:

A dedicated `tests/usb_instrumentation_runner.rs` rigorously resets the ServiceContainer and queue, exercises `process_usb_command_data_test`, and drains the queue into the Artisan channel so reviewers can see and replay the command. The wiring is gated to `target_arch = "riscv32"` and documented in `internalDoc/INSTRUMENTATION_README.MD`, ensuring the previously unused export now has a reproducible run path.

## Milestone Summary

**Decimal Phases:**

- None

**Key Decisions:**

- Adopt a dual mutex pattern (`EmbassyMutex` for async + `critical_section::Mutex` for ISR) to keep async access safe while preserving legacy sync paths.
- Gate async lock depth telemetry behind the `async-lock-depth-metrics` feature so production builds stay clean while host tests can inspect instrumentation.
- Reset instrumentation helpers before and after concurrency batches to keep `max_async_lock_depth` reproducible and avoid bleed-over between runs.
- Guard `process_usb_command_data_test` behind a riscv32 harness so the export is exercised without touching production tasks.

**Issues Resolved:**

- Eliminated the take/replace race window for sensor reads by migrating to `EmbassyMutex` and `lock().await` across all async callers.
- Proved ASYNC-06 compliance with the concurrent sensor read host harness plus lock-depth instrumentation and README guidance.
- Wired the USB instrumentation helper so `process_usb_command_data_test` is documented, consumed, and observable by auditors.

**Issues Deferred:**

- Deprecated sync helpers (`with_roaster()`/`with_roaster_mut()`) remain for ISR compatibility; plan to remove them once async callers and ISRs adopt the new API completely.
- `tests/mock_uart_integration.rs` still relies on the sync `roaster_sync` path; revisit after the async instrumentation harness is stable.
- The riscv32 instrumentation harness cannot be built on the host toolchain (`riscv32imc-unknown-none-elf` lacks `std`), so cross-target automation remains blocked.

**Technical Debt Incurred:**

- The dual mutex pattern and feature-gated instrumentation add conditional complexity that should be simplified once the async API is fully adopted.
- Legacy synchronization helpers stay deprecated for now but will need cleanup once ISR paths no longer require them.
