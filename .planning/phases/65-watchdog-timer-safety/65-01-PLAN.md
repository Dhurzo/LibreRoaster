  <action>
Create `src/safety/watchdog.rs` (guarded by `cfg(target_arch = "riscv32")`) that owns the esp32 Task WDT handle, exposes `WatchdogFeeder::initialize()` and `feed_async(bus_factor: f32)`/`last_failure_reason()` so the controller can log stage metadata, and records when the watchdog was reset. Extend `ServiceContainer` with a `watchdog_feeder` `Mutex<RefCell<Option<WatchdogFeeder>>>`, helper methods (`init_watchdog`, `with_watchdog`, `watchdog_available`) and the new `ContainerError::WatchdogUninitialized` case. Store the feeder once during boot so tasks can borrow it without double-moving the `ServiceContainer` singleton.

Update `AppBuilder::build()` to instantiate `WatchdogFeeder` after RoasterControl is initialized (e.g., grab TWDT peripherals via `esp_hal::peripherals::TWDT` or `esp_hal::task::TaskWdt::new(Configuration)`), call `ServiceContainer::init_watchdog()`, and keep the builder error flow consistent.

Add constants to `src/config/constants.rs`: `WATCHDOG_FEED_INTERVAL_MS: u64 = 100` and new default values for the fields added in Task 2 (e.g., `watchdog_feed_ok: bool = true`). Document the expectation that the feeder is pinged from the control loop.

<task type="auto">
  <name>Task 2: Feed the watchdog every control cycle and expose failures</name>
  <files>src/application/tasks.rs; src/control/roaster_refactored.rs; src/config/constants.rs</files>
  <action>
Add tracking fields to `SystemStatus` in `src/config/constants.rs` (e.g., `watchdog_feed_ok: bool`, `watchdog_last_failure: Option<&'static str>`). Update `SystemStatus::default()` so they start as `true`/`None`.

In `control_loop_task`, after `roaster.update_control` completes but before `Timer::after`, call `ServiceContainer::with_watchdog(...)` to `feed_async` and pass the latest `status.bean_temp` for logging. If the feed returns `Err`, set `status.watchdog_feed_ok = false`, store the failure reason, set `status.fault_condition = true`, log `warn!("SAFETY WATCHDOGFEED fail: {}", reason)`, and send a `SAFETY WATCHDOG` string to the output channel so instrumentation can observe the event. Only emit the string when the failure reason changes.

Also set `status.watchdog_feed_ok = true` when the feed succeeds so we report healthy loops. Keep the SAFETY line limited to one per failure and mark the control loop as needing a safe shutdown if the watchdog cannot be fed for two consecutive iterations.
  </action>
  <verify>cargo fmt -- --check && cargo check</verify>
  <done>Control loop pings the WatchdogFeeder each iteration, failure reasons update `SystemStatus`, and a SAFETY telemetry line is emitted before the loop sleeps.</done>
