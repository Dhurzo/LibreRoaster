  <action>
Create `src/hardware/ledc_guard.rs` with a `LedcGuard` that tracks the channel name, an `AtomicBool`, and the new `LEDC_GUARD_TIMEOUT_MS` (suggested 40 ms). `LedcGuard::try_acquire(name)` should return a `LedcGuardToken` while a `Timer::after()` detection fires a `LedcGuardError::Timeout` if the guard is held too long. Document that the guard must be dropped before any `await` (the token drop frees LEDC access).

Update `src/hardware/ledc_bus.rs` to use `LedcGuard`. Before touching a channel call `guard.try_acquire(entry.name)` and log a `warn!("SAFETY LEDC-GUARD timeout for {}", entry.name)` when a timeout occurs. On timeout, increment a new `SystemStatus::ledc_guard_timeouts` counter (add that field in `config/constants.rs`) and return early so the control loop sees the saturated state. Always release the guard token before returning from `with_channel_mut` and before any awaited operations.

If `LedcGuard::try_acquire` fails, record the failure in `SystemStatus` by calling a helper on `RoasterControl` (e.g., `status.ledc_guard_timeouts += 1`) so telemetry can later compare the counter. Keep existing LEDC duty logic but ensure the guard is dropped before panicking on errors.
  </action>
  <verify>cargo check</verify>
  <done>LEDC operations are guarded by the new timeout module and safety counters increment when the guard hits its timeout.</done>
