# Phase 83: Rust Modernization and Unsafe Surface Audit - Context

**Gathered:** 2026-03-07
**Status:** Ready for planning

<domain>
## Phase Boundary

Modernize the Rust firmware mechanically (cargo-fix/Clippy/rustfmt passes) while preserving every existing behavior and keeping a living register of the unsafe surfaces that remain. Unsafe surface justification, modernization evidence, and regression verification all stay within this phase; new capabilities are deferred to future phases.

</domain>

<decisions>
## Implementation Decisions

### Modernization scope & gating
- Run `cargo fix` + pedantic Clippy + `rustfmt` across the repo so modernization happens mechanically, trusting the automation suite to catch regressions.
- No additional rollback guardrails beyond the existing CI/CIT regression checks; failures simply block merges until resolved.
- Claude decides how to treat modules that touch strict hardware/control paths (e.g., pause automated passes, do targeted work, or skip them) so the modernization still respects behavior-critical code.
- Generate an auto-report after each run that summarizes which unsafe blocks changed so reviewers can see the impact immediately.

### Unsafe surface register & reporting
- The register stores just the location and the justification/note for each unsafe surface so it stays easy to review.
- Highlight register changes inside the dedicated modernization summary document (notified via repo artifact) instead of burying them in PR comments.
- Update the register periodically (e.g., once before the milestone sign-off) rather than after every run.
- When skipping modernization for safety reasons, log a brief note explaining why the code stayed untouched.

### Behavior equivalence verification
- Re-run a representative sample of command flows that cover every major module so the regression scope stays manageable while still exercising critical paths.
- Minor telemetry differences are acceptable if they stay within documented thresholds; we expect semantic outputs to remain equivalent.
- Use a hybrid approach: automated regression suites (cargo test/check) plus spot-check manual scenarios when a run touches sensitive modules.
- Record regression artifacts by referencing automation run IDs and storing the associated logs so auditors can trace what was compared.

### Developer experience for auditors
- Ship hybrid automation: CLI scripts that run standard passes and gather reports, but allow manual overrides or reminders when a maintainer wants to intervene.
- Store modernization signals via repo artifacts (e.g., `logs/modernization-summary.md`) so reviewers can inspect history without jumping into CI dashboards.
- Complement artifacts with a dedicated Markdown dashboard that surfaces progress, touched modules, and unsafe-surface deltas.
- Provide a documented checklist that describes the next steps (which suites to rerun, what to re-review) after each modernization run.

### Claude's Discretion
- Handling behavior-sensitive modules (deferred passes, targeted reviews, or outright skips) is left to Claude.
- Exact formatting/structure of the forced modernization summary artifacts and dashboard can follow existing conventions as long as the key signals are there.

</decisions>
